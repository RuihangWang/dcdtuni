# Exact source-component predicates (isolated candidate)

This is an isolated, read-only revision `codex/source-component-exact-20260927@b2b1cf08` of `source_component_validation.py` based on `329dda86`. **It is not mergeable as a general source-geometry gate:** a legitimate rotated plane becomes noncoplanar after the real writer's six-decimal STL quantization and remains an explicit XFAIL below. It is not wired to dcCart, `geometryTopology` admission, or CFD execution. It does not change any `.cfdproj`, export-time STL, or mesher input.

The validator first verifies each STL hash and parses the **same byte buffer** into both the established float summary representation and exact rational coordinates from the original ASCII decimal tokens. It then requires every triangle in one UID-bound solid to lie in one exact 3D plane. A dominant-axis projection gives rational 2D coordinates. Exact orientation and convex clipping distinguish a strictly positive footprint intersection from legal shared edges, including a rotated 10 m rectangle and the real Shinaide `Raised_Floor` T-junctions. No overlap-area tolerance is used. Exact 3D point-on-segment tests split nonconforming source edges in memory; only identical original 3D subedges join triangles. A separate 1e-10 m ambiguity clearance **rejects**, rather than welds, distinct vertices near another source edge. Before emitting the legacy rounded contour summary, the validator also requires the map from exact 3D vertices to rounded 2D output points to be injective; a separate RED→GREEN regression covers a collision despite the vertices being farther apart than the clearance. Neither check is a geometric pairing rule.

The three [previous RED cases](source-component-validation-review-red-2026-09-27.md) now pass: 5e-13 m² true overlap is rejected, 5e-13 m in-plane gap is rejected without joining, and projected shared edges 5e-8 m apart in 3D are rejected as multiple planes. The existing rotated shared-edge and nonconforming T-junction controls remain valid. Every component now returns `exactSourceTriangles`, a canonical sorted list of 3D vertices with each coordinate encoded as `[numerator, denominator]`. This is sufficient to reconstruct exact support. `triangleSetSha256` hashes this exact representation. A single-triangle fixture using `1` versus `1.000000000000000001` has the same float `sourceTriangles` but different `exactSourceTriangles` and authoritative digests. The float `sourceTriangles`, `projectedTriangles`, `projectedBounds`, `plane`, `areaM2`, and `boundarySegments` are **display-only** and must never decide physical relation admission.

Exact nonzero triangle area is checked before float area or projection. A six-decimal, exactly collinear triangle at `(0,0)`, `(3000,2342.331445)`, `(9000,7026.994335)` previously passed the public index with a false float area of about 1.86e-9 m²; it now fails. STL vertex lexemes are constrained **before** `Fraction()` to 64 characters, exponent magnitude at most 24, nonzero absolute coordinate at least 1e-24 m, and coordinate magnitude at most 10,000 m. This rejects an 11-character `1e-10000000` resource-amplification input without constructing its huge denominator. These are fixed bounds for this isolated data-center V1, not an arbitrary CAD import contract.

The original 354-source Shinaide export (`Shinaide.cfdrun` SHA-256 `c4e57c8022a29979401a887bcfa228071339e25a750a48cdaa7be6dc4a952dbc`) still yields 354 source faces, 354 components, 752 triangles, and `Raised_Floor` 45 display boundary segments. The latest full-summary SHA-256 is `e371429e53f168861a5460ae8abf766bfd7f516290a9f69917f9067bbcef9e91` (old float-identity digest `1b34b954...`); it changes because exact triangles and authority metadata are now included. Five warm-cache local runs had median 0.532570 s versus 0.047457 s for the earlier float candidate, about 11.2 times slower. See [machine-readable evidence](../../benchmarks/shinaide-source-component-exact-2026-09-27.json).

**Unresolved positive case:** `src/frontend/shared/js/stl_writer.js` writes each vertex with `toFixed(6)`. An ideal unit square rotated by `Rz(0.5) Ry(0.4) Rx(0.3)` has four coplanar vertices before export; their six-decimal STL values are not exactly coplanar (one rounded y coordinate differs by 1e-6 m from the sum of the other two). A two-triangle real-export fixture is retained as strict XFAIL: this exact-plane validator rejects it. Increasing one plane tolerance would allow some distinct near layers such as the 5e-8 m counterexample to be treated as one sheet. Formal admission therefore needs a `.cfdproj`-bound unquantized source face/connected component identity and an explicit export-rounding error budget, then separate predicates for true 3D support and allowed quantization. No such contract is implemented here.

The edge-splitting pass still scans all source vertices for each triangle edge, so exact rationals make large faces expensive. These source-level checks do not prove wall-pair identity, independent fluid gap width, inter-source support, mesh-stage cut support, `checkMesh`, or wind CFD validity. Geometry-focused and adjacent tests: 43 passed with the rotated case XFAIL. Do not promote this candidate to a production gate solely from the Shinaide result.
