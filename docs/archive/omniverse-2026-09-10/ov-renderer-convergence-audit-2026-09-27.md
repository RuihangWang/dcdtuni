# Shinaide React / Three.js / Omniverse contract audit

**Status:** design and CPU source/contract verification, 2026-09-27. This is not a live Omniverse rendering acceptance. The current user constraint is CPU-only development with a bounded multi-core budget; the earlier one-time GPU episode is over.

## Decision

Keep `.cfdproj` as the sole editable project. Compile its geometry and stable UIDs into a **derived, renderer-neutral scene**, then supply that scene to Three.js and OpenUSD adapters. Derive separate `.cfdrun` and `.liquidrun` execution inputs from the same saved project. Attach mesh and post-processing as typed, provenance-bound **result layers**, not as extra editable project geometry. The existing `dcdtuni.render-scene/v1` path is a useful CPU-proven visual snapshot from the built Three.js scene, but it is not yet a full interchangeable renderer contract.

The short-term implementation may continue using the built Three.js scene as the geometry compiler's output, since that is where current engineering detail, textures, valves, and pipes are actually present. A direct `.cfdproj → USD` exporter built separately would risk silently disagreeing with the browser's shared geometry builder. The long-term adapter boundary should be after one project geometry compiler and before either renderer, with explicit source UID, material, unit and transform records. Neither the Three scene nor a USD stage should become a second project truth.

## Exact current path

1. React builds model geometry under `globalGroup`. `RendererControl.snapshot()` calls `buildSceneSnapshot({root: globalGroup, project, camera, ...})` (`src/frontend/react/src/renderer/RendererControl.tsx`, `sceneSnapshot.ts`). The packet has project UID, primitive/model/equipment UIDs, project-space transforms, Y-up/metre coordinates, PBR fields, embedded PNG texture data, UVs and a physical time value.
2. `OvViewport` lazily connects the NVIDIA WebRTC SDK and sends the packet through `OvCommandClient`. The Kit bridge validates each transfer, authors `/World/RenderScene` and `/World/RenderCamera`, and sends a request-ID-correlated ACK (`OvViewport.tsx`, `ovProtocol.ts`, `dc.cfd_bridge/render_scene.py`, `extension.py`). Its ACK means USD authoring, not decoded video or rendered-pixel correctness.
3. The current OpenFOAM mesh preview is attached under `content`, **beside** `globalGroup` (`Viewport.tsx`, `__attachMeshPreview`). The wind-side post-processing group is another sibling under `content` (`Viewport.tsx`, `ppGroupRef`). Thus neither is traversed by the current OV snapshot. `RendererControl` subscribes to project edits and liquid result sample/render revisions, but no wind post-processing or mesh-preview revision. A wind field or mesh-layer change cannot by itself produce a new OV scene packet.
4. Wind surface fields, slices and streamline tubes use `ShaderMaterial` with raw scalar attributes and a LUT; the volume uses a ray-marching 3D texture (`postprocess/ppMaterials.ts`, `ppRenderer.ts`, `ppVolume.ts`). `sceneSnapshot.materialSnapshot()` intentionally rejects custom shaders. Merely changing its root to `content` would then fail conversion (or include editor controls) and cannot provide faithful field/volume rendering.
5. The full-screen OV video overlay is mounted over the retained Three viewport. It receives pointer input; Three's raycast, move/rotate gizmo, patch/pipe handles and mesh-preview interaction are not routed through the OV video. The bridge's separate, older demo supports CFD commands such as `setStreamlines` and `loadDataset`, but the React `OvCommandClient` exposes only scene/view commands and does not connect the React post-processing panel to that demo state. The old demo is not evidence that the integrated editor has those controls in OV.

## What CPU evidence establishes

- A real Shinaide browser export at physical 0 s and 600 s had 2,143 primitives and 25 texture identifiers per frame. UID/geometry/texture data were unchanged between frames, 29 material primitives changed with liquid temperature, CPU-authored USD reopened, 928 relative texture references per frame resolved, and compared point coordinates had zero recorded difference. See `docs/benchmarks/shinaide-dae-scene-export-2026-09-26.json` and `docs/archive/liquid-2026-09-10/shinaide-dae-workbench.md`. This checks **liquid-coloured model scene conversion**, not wind mesh/field conversion or OV pixels.
- CPU tests on Mac at `b41bb83f`: targeted React scene/protocol/view tests **52 passed in five files**. Mac `.venv` OpenUSD tests had **2 passed / 6 failed because `pxr` is not installed**, not because USD assertions failed. On the non-NSCC 40901 task worktree at the same checked HEAD, with four-core affinity, BLAS/OpenMP two threads and CUDA hidden, `test_render_scene.py` had **8 passed**. No Kit, RTX, GPU, WebRTC or new browser rendering was started in this audit.
- The previous authorized one-GPU live Kit episode made a signaling TCP connection but produced two browser `Omniverse connection timed out` outcomes, with no decoded video or scene ACK. The private Kit/Xvfb session was cleaned up. The subsequent ICD, worker-count, multipart-ACK and diagnostic changes are CPU-tested only; the timeout cause and live fix are still unverified. See `docs/benchmarks/single-gpu-kit-2026-09-26/README.md` and `docs/archive/omniverse-2026-09-10/ov-retest-plan-2026-09-27.md`.
- Shinaide's current wind mesh fails strict `checkMesh`, so its CFD result cannot be accepted as a physical prediction or as a genuine Shinaide wind post-processing visual acceptance. A separate known-valid OpenFOAM fixture can test the display contract without relabelling it as Shinaide prediction.

## Required derived contracts

**Geometry layer.** Compile every visible engineering primitive once from `.cfdproj` with project content hash, construction UID, optional equipment UID, optional source-face UID, primitive ID, explicit project-space matrix, metre/Y-up convention, indexed topology and PBR/UV texture descriptors. Validate against the actual built scene and exported STL where both represent the same physical face; render-only detail may remain outside CFD STL. Keep existing helper/gizmo filtering semantic. A missing model/source identity or unresolved texture fails the export rather than disappearing.

**Result layer.** Reference project content hash, run/input receipt, physical sample time, solver field and units, mesh receipt/polyMesh identity, patch or source-face UID mapping, visible patch set, colormap/range/opacity and layer kind. Use the existing decoded OpenFOAM mesh/field payloads as inputs, but define an explicit result-to-renderer adapter for boundary field, mesh edges, slices, streamline tubes and volume. Preserve raw scalars and LUT semantics where possible; if the USD renderer uses baked colours or a different volume implementation, label and test the resulting interpolation and lighting differences. Avoid forcing per-field mesh data into the 43 MiB Shinaide base scene JSON; send independently versioned layer updates and invalidate them when the run, mesh or field changes.

**View and actions.** Camera, selection and time remain renderer-independent. For full OV editing, route OV picked prim IDs back through stable model/source UIDs into existing React project actions, and map drag/rotate/gizmo coordinates to project metres. React remains the undo/redo and geometry-edit authority. UI control actions for mesh visibility, field/range, slice, streamline and volume must update shared view/result-layer state, so switching does not create separate Three and OV settings. Until those commands exist, OV is a read-only scene viewer and the UI must not imply that the editing gizmos and wind post-processing controls work there.

## Acceptance gates

1. **CPU schema and conversion:** Save/reopen one `.cfdproj`; derive `.cfdrun`, `.liquidrun` and scene from the same content hash. Validate UID uniqueness, world transforms (including mirror/rotation), Y-up/metres, material group/draw range, UV wrapping/flip, all referenced texture bytes and missing-identity rejection. Reopen a CPU USD stage and compare geometry, source identity, field sample time and material/shader connections.
2. **CPU result layers:** With a known-valid OpenFOAM run, inspect actual polyMesh patch faces/edges, boundary field values, two physical times, hidden patches, slice plane and streamline seed/set geometry. Reject stale run/mesh/time/field mappings; test both render adapters against the same typed layer state. Include the Shinaide mesh only after its quality gate passes.
3. **CPU interaction protocol:** Unit/integration tests for OV prim selection → React UID, project edit/undo → new derived scene, rotate/translate coordinates, camera/selection/time round-trip and panel toggles for field, mesh, slice, streamlines and volume. A scene ACK must be tied to the project/run/mesh revision represented by the packet.
4. **Later live OV acceptance:** When GPU use is separately authorized, require decoded video pixels plus scene/view ACK for the real saved Shinaide project. Verify geometry/texture appearance, mesh and post-processing against accepted inputs, edit/gizmo/rotation, streamlines and field time change, then OV → Three preservation. TCP signaling, CPU USD authoring and HTTP 200 alone do not pass this gate.

No GPU-dependent visual claim can be completed under the present CPU-only instruction. This audit leaves the existing Three.js and OV code unchanged.
