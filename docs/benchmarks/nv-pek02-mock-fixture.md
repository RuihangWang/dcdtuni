# NV PEK02 inventory mock — project-owned DAE fixture

This is an **assumed software-test case**, not a PEK02 reconstruction, a calibration, a measured response, or a control-performance result. The editable source is [`NV_PEK02_mock.cfdproj`](../../case/NV_PEK02_Mock/NV_PEK02_mock.cfdproj). The numerical input is derived through the existing React/shared compiler and is never edited as an independent graph.

- `C31`: 34 energy valves. The fixture assumes one rack per energy valve; the rack allocation itself is not established by this cell.
- `C40`: 68 isolation valves. These are valves, not 68 racks.

Source SHA-256: `ec4dc0ee243bdd7e26ecab44791f84039e0f5bbf2317fb1355f93e7780213075`. The generator refuses a different point-list hash. It does not count the repeated CDU comparison sheet. The point list does not prove installation, telemetry availability or command authorization.

## Explicit assumptions in the saved project

- Two independent CDU zones, 17 equivalent racks each; no common header, cross-tie, redundancy or failover claim. Each CDU uses one **equivalent** pump and HX, not a reconstruction of the table's internal three-pump arrangement.
- Each rack has one energy valve followed in series by one supply isolation valve, plus one return isolation valve. All 102 valves are fixed fully open. Return tees are separate assumed fittings and are not counted as NV valves.
- Isolation valves are zero-volume hydraulic elements co-located with an existing branch fitting. The saved `seriesWithValveId` references determine the series connection; no second parallel rack connection is created. The common geometry-derived pipe lengths and fluid volumes remain intact. Closing an ideal valve changes its active set and is outside this fixture's admitted test.
- Generic geometry is cloned from the project's own `Shinaide_hybrid_cpu.cfdproj` and reconfigured: assumed room 22 × 14 × 4 m, rack pitch 0.85 m, 50 mm headers/spokes and 25 mm rack manifolds. The source template is hashed; these dimensions are not NV CAD. The existing frontend compiler retains capped header tails.
- One equivalent 10 kW liquid heat load per rack: 340 kW initially, 408 kW after an assumed 20% step at 5 s. Horizon 10 s, step 1 s, 11 samples. These are test inputs, not measured IT powers or an identified IT-to-liquid heat fraction. Equivalent load parameters are `R_th=0.0004 K/W`, 20 kPa at 18 L/min, `C_solid=50000 J/K`, fluid volume 2 L; no individual GPU or cold-plate identification is claimed.
- Synthetic pump curve `H0=12 m`, `a=300000 m/(m³/s)²`; valve `Kv_max=12 m³/h@1bar`, linear characteristic, `D=25 mm`; each HX has `UA=45000 W/K`, quadratic resistance 120 Pa/(kg/s)² and linear resistance 1000 Pa/(kg/s). These are a mock parameter pack, not NVIDIA/Vertiv data.
- Both primary circuits explicitly prescribe 5 kg/s at 293.15 K, with 50 L primary and secondary mixed volumes. Water properties are 997 kg/m³, 4182 J/(kg·K), 0.00089 Pa·s and 0.606 W/(m·K), chosen as constant mock values. The HX is the v3 two-mixed-volume model, not an infinite temperature reservoir or a vendor counterflow performance curve.
- `analysis={mode:transient, initialization:steady}` and Newton tolerances are saved in `.cfdproj`. No PID, equipment-efficiency model, electrical-power measurement or energy-saving claim is included.

## Reproduction and compilation

From the repository root, using the already installed React development dependencies:

```sh
nice -n 10 node tools/generate_nv_mock.mjs
nice -n 10 node tools/generate_nv_mock.mjs --check
```

Use `--point-list /path/to/Pek02_BMS_PointList_Interface_V3.0_20260916_CQB.xlsx` on another host. `--project` and `--output` select output locations. `--check` compares exact regenerated bytes without writing files. The tool sets one Go/Node worker for bundling, builds no UI, starts no service and runs no solver.

The actual chain is:

`.cfdproj → normalizeStateV4 → compileSavedExperiment → compileDynamicLiquidGraph → shared liquid_graphgen → strict v3 .liquidrun`

The dynamic compiler adds explicit project-owned series valves to the already compiled rack spokes. Its shared document validator rejects duplicate fitting UIDs, missing/foreign branch references, contradictory extra rack connections, zero opening and unsupported non-coincident placement. The v3 schema and primary-circuit adapter are the application's existing implementations.

Outputs:

- [`nv-pek02-mock-v3.liquidrun`](fixtures/nv-pek02-mock-v3.liquidrun): 316 nodes and 348 edges: 208 pipes, 102 valves, 34 equivalent cold plates, 2 pumps and 2 HXs.
- [`nv-pek02-mock-v3.compile.json`](fixtures/nv-pek02-mock-v3.compile.json): source hashes, every one of the 102 asset-to-edge bindings, assumptions, and two connected components of 158 nodes each.
- [`nv-pek02-mock-v3.validation.json`](fixtures/nv-pek02-mock-v3.validation.json): actual strict backend admission and parameter-assembly evidence.

## Initial schema-admission validation snapshot

The frontend fixture and series-valve tests passed with one Vitest worker. Re-running the generator with `--check` reproduced the saved project, derived input and mapping report byte-for-byte. The real `load_dae_input` then admitted the derived v3 manifest on 40901 using the `dcdtuni` environment, CPU affinity of one core, one PyTorch/BLAS/OpenMP thread, lower scheduling priority and no visible CUDA device. It constructed 4,396 float64 parameters and confirmed the authored load event changes the sample-5 parameter vector.

```sh
python tools/verify_nv_mock_input.py --report docs/benchmarks/fixtures/nv-pek02-mock-v3.validation.json
```

At that initial schema-admission stage, no solve, residual-convergence check,
conservation experiment, finite-difference gradient check, performance benchmark
or closed-valve event had run for this 34-rack case. Schema admission and graph
construction alone did not establish transient correctness. No NSCC host was
accessed and no GPU process was started for this fixture.

and bounded CPU1/CPU2 timings](nv-vectorized-cpu-2026-09-26.md), [heat/pump/positive
