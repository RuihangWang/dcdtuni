[P2 source integration gap A] Destructive terminate may run before the connect promise settles.
In AppStreamer.connect (installed character 716850 onward), the Direct object is assigned to static _stream synchronously and passed to the asynchronous connect routine. Direct._connect (704919–708400 region) awaits platformDetails, initialization and launch. AppStreamer._streamStatus is only assigned connecting after the Direct connect promise returns inProgress (717700–718000 region). During that initial await the static status can still be none(0).
A legal call sequence is open -> pending SDK initialization -> close -> terminate(false) while SDK status is still 0. Since this is not the special connecting(1) branch, AppStreamer invokes Direct.terminate(false); Direct._terminateStream can find _ragnarokApp still null, then reports success. The static completion clears _stream=null. The original Direct._connect continuation still holds the old Direct object and can create/start its runtime and later change static status to 1 or 2. The exported controller reference has been discarded; public terminate can no longer reliably reach that old object. This follows actual source evaluation/await ordering. No test/probe was run to instantiate it. Simply adding another eager terminate does not repair this detached-controller sequence.

[P2 source integration gap B] Promise completion and onStart event can overwrite each other's stream status.
The SDK onStart wrapper sets connected(2) for success, error(4) for failure, and if prior status is cancelled(3), changes the event to canceled and triggers terminate. Separately the SDK connect promise .then unconditionally changes status to connecting(1) when the return is inProgress. Thus either ordering can lose prior lifecycle intent: a late connect promise can overwrite cancelled(3), or it can overwrite connected(2) after onStart has already happened. AppStreamer.terminate while status==1 only changes it to 3 and returns inProgress; it does not call Direct.terminate. If onStart has already happened, there may be no later event to finish the stop. The application then polls forever until its 15-second deadline and permanently blocks future opens. The existing fake connecting-cancel test manually sets status to none and does not exercise this real SDK overwrite; the late-promise test manually changes idle and only verifies that the idle gate waits, not that cleanup drives SDK termination.

A third observation matters for diagnostics: SDK none proves its exported controller/status have been cleared after Direct.terminate's success return, not an independent remote/video shutdown receipt. Direct._terminateStream calls async stopButtonClick without awaiting it, destroys the DOM delegate, sets _ragnarokApp=null and clears controller metadata. The lower stream client's stopStreaming kicks its stop/cleanup state machine; later stop callbacks may still arrive. The retained DOM delegate destroy stores its original parent reference and safely removes listeners/ResizeObserver even after the React node was detached, so this source does not justify blaming missing DOM elements as the main cause. The normal public API may work correctly for a settled connected runtime, but no browser stop/reconnect proof is obtained from its success object alone.

Minimal repair plan (preserve the lease owner):
1. On close, record cancellation intent immediately, prevent queued viewers starting, and await the original SDK connect/init promise under the same bounded cleanup deadline before calling a destructive public terminate. A failed/rejected connect also needs cleanup if a controller could have been created. If initialization never settles, keep the owner blocked and use a document-runtime teardown path; do not connect a second singleton.
2. Track the distinct terminal onStart lifecycle receipt (success/error/canceled) even when the React viewport is disposed. Record that receipt before the disposed guard; do not run scene transfer or callbacks for disposed views. Do not treat the connect promise's inProgress response as onStart success. OvViewport's current started boolean is set for any first message and is suppressed entirely after disposal, so it is not a usable shutdown receipt as written.
3. After initialization is settled, terminate serially. If SDK marks status 1->3 and onStart has already finished, a subsequent real terminate is needed to clear the stale connecting state; it must not overlap an existing SDK auto-termination. If onStart is still pending, leave the cancel marker until the SDK wrapper handles that event, then confirm idle. Avoid blindly setting SDK private fields or invoking parallel stops. Already-terminating errors must wait for the same owner's completion, not launch a new connection.
4. Publish close success/failure as an application lifecycle transition so the selector can indicate waiting cleanup or a recovery action. Preserve the local project/camera and return Three promptly; do not hide a permanent blocked lease until the next OV attempt. Keep the barrier on any uncertain cleanup failure.
5. If the installed SDK has already detached its controller, permanently failed, or cannot finish callbacks, a fresh isolated iframe/document per viewer is a defensible containment design. Its own SDK import/singleton/video/runtime are scoped to that document, while the parent retains engineering state and proxies only the existing command/ACK transport. Destroy the previous document/runtime before allowing the next runtime owner. This is not permission to connect two viewers or to reset the same stuck singleton. A normal browser check must establish old media/worker/channel shutdown, including cancel during init and late callbacks, before calling this reliable recovery.

Meaningful narrow verification cases for the implementation owner (not executed here):
- Pending initialization with status0: close must not destructively terminate before initialization settles; a late initialization may never orphan a live Direct object.
- SDK connect inProgress arriving after canceled or after terminal onStart: the same owner must finish teardown and release a queued next viewer only after confirmed cleanup.
- onStart already terminal + SDK status1 stale: cleanup must progress beyond the marker-only terminate response.
- onStart absent/hung init: deadline refuses reconnection in that document; an explicit isolated-runtime destruction may recover without a second live owner.
- Failed/throwing terminate and already-terminating SDK callback: bounded failure/retry, no double stop/connect, no swallowed uncertainty.
- Queued viewer canceled before ownership: existing no-connect/no-terminate invariant retained.
- Real normal live OV -> Three -> OV and fast cancel/re-entry, with old/new client lifecycle timestamps and media state, exact engineering project/hash/camera maintained; no extra Kit/GPU owner.

Diagnostic improvement: include the last public streamStatus, connect-settled flag, terminal onStart receipt, stop attempt result/action/status/info and elapsed time in a bounded token-free trail. Current String(failure) loses SDK error objects as [object Object], while the generic timeout does not distinguish init still pending, marker-only cancellation, terminal SDK failure or stale callback. These observations are needed to match this source diagnosis to ROOT's actual browser failure; they do not require logging scene payloads or session credentials.
