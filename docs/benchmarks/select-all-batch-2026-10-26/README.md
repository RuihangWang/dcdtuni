# 全选后的几何重新合批（2026-10-26）

**结论：GTC 全选后每帧绘制调用由 3,477 降到 130，画面与改动前逐像素一致。**

## 原因

PROJECT_STATE 原先记的是“拖动时淡化的边线改为合批绘制”。在无头 Chromium（软件 WebGL）中实测，Shinaide_Liquid 与 GTC 上的边线在全选、拖动透明度和提交之后都仍在合并的边线批里，单独绘制的线只有 1–2 条。真正的开销来自网格：

- 选中高亮给每个被选网格换上它自己的材质克隆（`interaction/selectionHighlight.ts`）。
- 静态合批按材质对象分组，每个克隆自成一组，于是这些网格全部退出合批、各自绘制。
- GTC 全选后，单独绘制的网格由 15 个增加到 3,461 个，每帧调用由 48 增加到 3,477。

## 修法

- **按外观分组。** `geometry/staticBatch.ts` 的网格按材质的外观签名分组（类型、颜色、自发光、粗糙度、贴图等），不再按材质对象。
  - 成员共用一个材质时，合批直接用它，与原先相同。
  - 成员是外观相同的克隆时，合批持有第一个的副本；某个成员的外观随后改变（例如被设为活动模型而变亮），它就退出合批。
  - 带着色器钩子或裁剪平面的材质仍按对象分组。
- **选择稳定后重建合批。** 视口（`components/Viewport.tsx`）在至少 64 个网格退出合批、且这一数目保持一个稳定期（400 ms）后，重建一次合批。紧接着的再次重建等待时间加倍，所以持续变化的材质不会让合批反复重建。

## 测量

在无头 Chromium、软件 WebGL、1600×1000 下测量，数值为每帧绘制调用数（`renderer.info.render.calls`）。

| GTC | 改动前 | 改动后 |
|---|---:|---:|
| 未选中 | 48 | 46 |
| 全选（75 个模型）稳定后 | 3,477 | 130 |
| 拖动“整体透明度”期间 | 3,465 | 3,465 |

- **像素对比。** 同一工程、同一视角下全选，把“重建合批”的构建和“不重建”的构建各截一张：3D 视口逐像素相同，差异只出现在操作日志的时间戳上。
- **测试。** `test/staticBatch.test.ts` 新增 3 项：
  - 高亮克隆重建后合批，并由合批持有材质副本；
  - 外观变化的成员退出合批，副本在销毁时释放；
  - 带钩子的材质不按外观合并。

## 适用范围

透明网格仍各自绘制，例如拖动透明度时和透明度低于 100 % 的模型。Three.js 要按每个物体的深度对透明物体由远到近排序，才能得到正确的遮挡与混合；合进一个批次后，批次之间的顺序只能按整批排，会改变画面。

只读的视图淡化（后处理的模型透明度、网格预览）已有单独的合并绘制 `geometry/fadeGhost.ts`。
