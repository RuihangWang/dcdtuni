# Bounded single-GPU Kit acceptance attempt

This records runtime startup and cleanup evidence. It does **not** establish successful scene transfer, rendered Shinaide pixels or seamless switching. Browser evidence is maintained separately by the main task.

The preceding numerical CUDA phase and these two sequential Kit attempts shared one unchanged eight-minute deadline: epoch `1790435607.078577`. The only authorized physical device was GPU 0, UUID `GPU-dd97ad37-4a36-19df-d789-0ee503ba4d93`, PCI `00000000:16:00.0`. Each Kit start freshly verified that exact UUID/index/PCI and an empty compute-app list. CPU affinity was `[0]`, nice 10, BLAS/OpenMP threads 1; renderer multi-GPU was disabled and the CUDA UUID mask exposed only logical `cuda:0`. No AI worker or training process was started.

The runtime was the existing main-tree `omni.cae_streaming.kit.sh`; the extension loaded through `--ext-folder` came from the isolated task worktree. Main source was not changed. Private Xvfb displays were allocated with `-displayfd`, yielding `:0` on both sequential attempts. The other user's `:99` display was not used or stopped. Each attempt has its own process receipt, stdout log and Xvfb log below; the second reused only the first attempt's private runtime data/cache/config.

- **Attempt 1:** Kit PID `3355008`, Xvfb PID `3354760`. The existing Kit build initially lacked `omni.kit.livestream.messaging`. Kit's own dependency resolver automatically fetched official `omni.kit.livestream.messaging-1.3.3+109.0.0` into this attempt's private data directory; this was not a manual installation and did not modify main. The main task requested a stop while that startup state was being investigated. The process group received SIGTERM, then SIGKILL after the bounded grace period; Xvfb exited normally. Elapsed `70.757 s`. Logs and receipt remain intact.
- **Attempt 2:** Kit PID `3357967`, Xvfb PID `3357964`. Both messaging and the worktree `dc.cfd_bridge` started successfully. Kit reported `app ready` at `53.785 s`, followed by `native UI hidden`. TCP `0.0.0.0:8301` was owned by this Kit process. A real external browser connection from `10.91.82.130` was observed. The Vulkan inventory showed only device index 0 as `Active: Yes: 0`, with UUID prefix `dd97ad37` and Bus ID `16`; all other enumerated rows were inactive. The driver listed duplicate Vulkan entries, so the recorded physical UUID/PCI association, not GPU-row count, identifies the device.

During the first render work, Kit logged RTX/OptiX initialization on device 0 and `carb.tasking is likely stuck` warnings, followed by emergency helper-thread creation. Those threads inherited the same one-CPU affinity. Near the deadline, the external signaling connection had closed and the private texture directory still contained zero files. No completed snapshot authoring was established from these observations; TCP connection alone is not acceptance.

The second attempt automatically stopped at the shared deadline with ten seconds reserved for cleanup. Kit and Xvfb both exited with code 0. Completion epoch was `1790435597.94381`, **9.135 s before** the unchanged episode deadline. Its elapsed runtime was `160.414 s`.

Post-cleanup checks found both Kit PIDs and both private Xvfb PIDs absent, no TCP listener on 8301/8378, and only the authorized GPU was queried: GPU 0 returned to `5 MiB`, `0%` utilization and an empty compute-app list. No further GPU run was launched.

The controlled launcher and its CPU-only plan tests are [`kit_acceptance_harness.py`](../../../tools/kit_acceptance_harness.py) and [`test_kit_acceptance_harness.py`](../../../tools/test_kit_acceptance_harness.py). The initial eight tests passed before GPU execution. `--execute` is required for any GPU metadata probe or process launch; without it the harness prints only a plan. A private `stop.request` asks the supervisor to clean up only its own newly created process groups, with no port- or name-based process termination.

## CPU-only postmortem

The main task's browser verification recorded **two `Omniverse connection timed out` outcomes**, safe fallback to Three.js, no remaining video element and no scene ACK. The selected run 737 and its t=0 state survived; the main task later restored t=600. Exact client-click epochs were not included in this Kit receipt, so the two client attempts cannot each be precisely aligned to server initialization from this file alone.

The server evidence narrows the issue without proving one root cause:

- A missing USD stage is not supported by the log: `World0.usd` and its session layer were loaded at 15:11:29 UTC. App readiness followed at 15:11:31, and the actual stream server started on TCP 8301 / UDP 47998 at 15:11:34. These milestones did not guarantee an encoded frame or open data channel.
- RTX initialization continued afterward: the OptiX adaptor for device 0 was created at 15:12:16, around 42 s after stream-server startup. There were 58 tasking-starvation warnings and 4,460 repeated `createViewportImpl` log entries in attempt 2. The one-CPU/one-task-worker constraint is relevant context, but the warnings do not independently prove it caused both client timeouts.
- Kit explicitly reported duplicate Vulkan Installable Client Drivers. A subsequent **file-only** inspection found `/etc/vulkan/icd.d/nvidia_icd.json` and `/usr/share/vulkan/icd.d/nvidia_icd.json`, both describing NVIDIA `libGLX_nvidia.so.0` with different manifest/API versions. This is a concrete runtime configuration defect. A process-local `VK_DRIVER_FILES` pointing at one verified manifest can avoid duplicate discovery without deleting or changing system files; that mechanism is documented by the [Khronos Vulkan loader](https://github.com/KhronosGroup/Vulkan-Loader/blob/main/docs/LoaderDriverInterface.md). It has not been GPU-tested here and is not yet established as the timeout cause.
- ICE/media blockage and encoder failure remain **unproven**. The official installed WebRTC extension sets the `omni.kit.livestream.streamsdk` log channel to `error`, and these logs contain no selected ICE candidate-pair, completed-media or encoder-ready evidence. The browser-side SDK's documented callbacks support connection-status and stream-stat diagnostics, but the current adapter did not retain those details. An established signaling TCP connection cannot settle this distinction.

The next CPU-only preparation is therefore to make the per-process ICD selection explicit and capture SDK/StreamSDK readiness diagnostics. Simply extending the client's 15 s timeout is not an evidence-backed correction. Positive pixel-stream, data-channel ACK and t=0/t=600 switch acceptance still require a separately authorized live GPU validation after those checks. No further GPU operation was performed for this analysis.

Structured observations are saved in [`diagnosis.json`](diagnosis.json). The full local logs and process receipts remain in `attempt1/` and `attempt2/`.

## CPU-only harness corrections after the failed episode

The repository harness was subsequently corrected and checked with **12 pure plan tests**. These changes were not executed against a GPU, Xvfb or Kit, and they do not establish that the stream timeout is fixed:

- `--vulkan-icd` defaults to the existing `/etc/vulkan/icd.d/nvidia_icd.json`. The plan reads and hashes that single manifest, checks it names the NVIDIA `libGLX_nvidia.so.0` library, and places the same absolute file in both `VK_DRIVER_FILES` and `VK_ICD_FILENAMES`. The newer variable takes precedence when supported; the older one covers older loaders. The execution environment clears inherited additive/filter driver variables. No system manifest or main-tree file is changed.
- The initial harness **did** explicitly force `carb.tasking.plugin/threadCount=1`. The first CPU-only correction changed that to `2` process-local task workers while retaining CPU affinity `{0}`, single-thread numerical libraries and TBB maximum one. This was a prepared configuration, not a new live run. The subsequent explicit small-CPU-budget update below supersedes that single-core restriction. Whether the logged starvation disappears requires a future live test.
- An opt-in `--stream-debug` adds the exact current-runtime setting `--/log/channels/omni.kit.livestream.streamsdk=info`. The installed WebRTC extension's `config/extension.toml` otherwise pins that channel to `error`. This option only prepares a future authorized run; it does not start anything by itself.

The existing NVIDIA JavaScript SDK 5.18.2 accepts `streamConfig.onUpdate`, `onStart`, `onStop`, `onTerminate`, `onStreamStats` and `onCustomEvent`. A future diagnostic pass can record the callback's actual action/status/info and stream statistics while retaining normal errors and ACK semantics. No frontend changes or connection-timeout increase were made in this correction.

The attempts' saved `state.json` files retain their **original** one-worker launch arguments; they must not be mistaken for runs of the corrected harness. The authorization for this episode is consumed, and no new live run was attempted.

## Explicit CPU budgets after the resource-policy update

The user subsequently removed the one-core restriction while retaining the requirement not to consume the host's full CPU quota. The candidate for a future separately authorized Kit run is now `--cpus 0,1,2,3 --numeric-threads 2`: four explicitly selected logical CPUs, four Kit tasking workers, two OpenMP/MKL/OpenBLAS/NumExpr threads, TBB maximum two, and nice 10. This is a bounded candidate, not a GPU launch or new GPU permission.

`--cpu N` remains supported as the legacy single-index syntax; with no CPU option, the default remains CPU 0 with one numerical-library thread and two tasking workers. The new mutually exclusive `--cpus` accepts a comma-separated list of at most eight distinct nonnegative indices. It rejects duplicates, ranges, `all`, empty values and conflicting old/new options. Numerical threads default to `min(2, selected CPU count)` and must be an explicit positive count no larger than that set. No host-wide CPU-count detection automatically expands the budget.

Before any child starts, the harness checks that the requested set is contained in the supervisor's allowed affinity, applies it and reads it back. Both Xvfb and Kit use the same owned-process launcher, which checks the supervisor mask again immediately before spawning; children inherit that verified mask. The receipt records effective affinity and niceness. This check respects inherited cpuset limits but does not by itself establish a cgroup CPU-time quota. The main task's host read found 48 logical CPUs allowed at that time; the inspected `cpu.max` path did not exist, so no absence-of-quota claim is made.

The updated source passed **32 CPU-only tests in 0.64 s**, including actual short Python-child inheritance under both one-CPU and four-CPU masks, without launching Kit/Xvfb or enumerating GPUs. The single NVIDIA ICD, one GPU UUID, deadline and owned-process cleanup policies remain unchanged. The original single-core failure receipts are retained exactly as executed, and the changed budget has not yet been used for live OV acceptance.
