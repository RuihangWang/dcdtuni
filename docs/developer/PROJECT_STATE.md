## 已经可用

### 风冷主线

从编辑器到收敛判定的链路已经闭合：React 编辑器导出 `.cfdrun` v4（只在根级保留一份 `simulationConfig`）→ dcCart 切割单元网格（默认引擎，MPI 原生，单进程只是一个 rank 的特例）→ 严格 `checkMesh` 质量回执与 patch 对齐门 → 求解前边界条件审计（`bc-audit.json`）→ 仓库自建的 `buoyantBoussinesq{Simple,Pimple}Foam_new` → 按 ACU 回风温度判收敛并自动停算。

- **十个发布算例全部通过**：Base_leakage、Tri_angle、Slab、STDCT、CMI-China、Base604、Base2-9、DAML-Testbed、Shinaide、Shinaide_Liquid 经 React 流程重网格后严格 `checkMesh` 全过，最近一次稳态求解都判为 `CONVERGED`。回执摘要见 [air-release-cases-2026-10-21](../benchmarks/air-release-cases-2026-10-21/README.md)，提交 `a69b81e97`、`31e65b349`。dc-builder 示例在 `meshBaseSize` 0.34 m 下曾因一处带挡板面的角落碎块报 small volume ratio；dcCart 新增末轮 `baffleCrumb`，在交出的每个面都守住边界偏斜时把这种碎块交给固体，该算例现在通过严格门槛，十个发布算例重网格后与 10-21 回执逐字节相同（[回执](../benchmarks/dccart-034-volume-ratio-2026-10-22/README.md)）。Shinaide 的地板开孔原先与设备脚印错开 1–10 mm，留下的缝让气流绕出房间，墙、地板、天花板因此没有边界面；开孔按设备当前脚印对齐后重网格，房间外壳闭合，严格 `checkMesh` 通过，重解按回风判据收敛（[回执](../benchmarks/shinaide-floor-cutouts-2026-10-22/README.md)）。

### 液冷

- **可微 Newton DAE** 是生产求解器：稳态、后向 Euler 瞬态、一致初始化与隐式伴随；输入是严格的 `.liquidrun` v3/v4（v4 由 cfdproj v5 时间轴编译而来）。React 液冷工作台新实验默认走 DAE，服务器运行会话 `/api/liquid/runs` 支持在线指令、独立稳态查询、checkpoint 与已执行输入重放（[liquid-runtime-api.md](liquid-runtime-api.md)、[liquid-dae-workbench.md](liquid-dae-workbench.md)）。
- **本构律**：泵按相似律 `H = N²·H₀ − a·Q·|Q|`（停泵或降速时能耗散反向流）；摩擦在低雷诺数处无奇点；静水压计入每条边并检查回路高程闭合；每台 CDU 可选逆流 ε-NTU（新建默认）或混合容积（旧文件按原模型回放）；停滞回路与无稳态给出明确报错。所用定律版本写入每个结果的 `solver_laws`，旧运行恢复时标为推断。
- **大规模网络**：未知量超过 4000 时，Newton 与隐式伴随自动改走稀疏线性代数（`solver/dae_sparse.py`：按列着色的方向导数组装 Jacobian、SuperLU 分解、伴随复用同一分解；每步按行用一次随机方向的精确导数校验，流向反转或升温后才出现的依赖就地补进稀疏结构）。Shinaide 管网加密到两万多未知量时，稳态加梯度在 CPU 上一分钟左右完成；负荷阶跃的瞬态每步走稀疏 Newton，比稠密明显更快、内存更小，值、芯片温度曲线与梯度都和稠密路径一致（[liquid-dae-sparse](../benchmarks/liquid-dae-sparse-2026-10-22/README.md)）。已保存的工程不受影响：4000 以内仍走稠密路径。
- **液冷前端**：求解页分五段并有实时就绪检查；结果页有管网表（实际流向、流量、流速、压降）、热量与换热器、各对象曲线和风液混合热量账本；3D 中管网可按温度、流量、流速或压力着色并有色标，流向箭头沿管路画出、方向为实际流向、大小随流量、颜色随流速，可动画；Kit 端用同一规则着色和画箭头。已在浏览器里端到端核对（稳态求解、流量着色与箭头方向）。
- **数值验证**：全环制造解时间阶趋近一阶、隐式伴随与中心差分一致、CPU 与 GPU 前向一致，回执见 [liquid-current-glycol25-jacfwd](../benchmarks/liquid-current-glycol25-jacfwd-2026-10-13/README.md)、[liquid-full-mms-asymptotic](../benchmarks/liquid-full-mms-asymptotic-20261007/README.md)、[liquid-fullcase-gpu-parity-gradient](../benchmarks/liquid-fullcase-gpu-parity-gradient-20261007/README.md)。全环制造解里粗步长下换热器二次侧的终时刻阶数门仍为原样登记的 RED，原因已查清：产品与独立的后向 Euler 误差递推逐级一致，阶数随步长加密单调趋于一；粗步长偏低来自该时刻一阶误差系数刚过零点、二阶项尚不可忽略，不是求解器缺陷，邻近的制造解在同样的粗步长下都在阶数带内（[liquid-mms-hx-order-cause](../benchmarks/liquid-mms-hx-order-cause-2026-10-22/README.md)）。设备参数目前都是合成 mock，不是现场标定。

## 2026-10-29 snappy 网格的质量检查一直不通过（已修复）

- 原因：snappyHexMeshDict 的 `maxBoundarySkewness` 是 snappy 常用的 20，而严格 checkMesh 对所有面（含边界面）都按偏斜度 4 判。snappy 因此保留了检查会拒收的边界面：DCTS_0112 自 10-27 导入起，每次出网格都有同样 2 个偏斜度 4.32 的壁面面片（一台服务器的顶面），出网格时与手动「检查网格质量」都判为未通过。

- 同日，网格变更判别的两处误判（队友看到「网格记录来自旧版本，需要刷新一次」引出）：dcCart 网格身份含有根级 `meshConfig` 里的界面显示开关（`locInMeshVisible`、`blockMeshEditActive`、`blockMeshMoveMode`），在网格页勾一下「显示」locationInMesh 就会要求刷新、并拒绝 solve-only；身份升到 v5，去掉这三项（旧回执仍按 v4–v1 匹配）。另外判别原来只比 STL，改基础尺寸、加密级别或引擎时 dcCart 显示「刷新一次」、snappy 显示「一致」，网格都不会重出；现在与网格当时的清单比较网格设置（两边都有的键，进程数与显示开关除外），不同即判为 `geometry`（reason `settings`），提示列出改动的键并禁用求解。浏览器实测（Base_leakage 副本，dcCart）：出网格后勾选显示仍为「一致」；基础尺寸 0.25→0.2 后提示「网格设置已改动（baseSize, blockMeshBounds, meshBaseSize），需要重新生成网格」、执行求解禁用；撤销后恢复「一致」。

## 2026-10-29 AI 推理：TTA 分块、自动切换与 GPU 实时显示（已完成）

- 起因：Base2-9（dcCart，870 万节点，训练房间的 6 倍）AI 推理显存不足。整网格一次前向的显存随房间增长（DCTS 房间约 11 GB，Base2-9 约需 64 GB），24 GB 的 4090 放不下；启动时的预热也在这个房间上跑整网格，同样爆显存并留下 9.4 GB 缓存不还。
- 推理方式（AI 推理页）：自动 / 整网格 / TTA（重复次数 R）。TTA 即论文的 test-time aggregation：节点池按训练时一次采样的规模分块，每块取 2 层邻域子图、按训练方式抽锚点，按覆盖次数平均；种子固定。自动：整网格的预估峰值放得下就整网格，放不下就 TTA，整网格仍爆显存时自动改用 TTA 重跑；模型卡可设自动优先 TTA。实时调参与 AI 初始化同样遵从。
- 显存估算：峰值 = 节点系数 × 节点数 + 行系数 × 单次前向行数，按两模型实测拟合（SCANO 误差 ≤0.05 GiB），房间跑过一次后用实测值。AI 推理页每 2 s 显示所用 GPU、已用/总显存、推理可用显存、AI 进程占用、房间节点数、本次将用的方式与预估峰值。
- 精度（判据先登记再测，[回执](../benchmarks/scano-tta-2026-10-29/README.md)）：4 个 DCTS 示例房间对 CFD 真值，SCANO 整网格 0.4060 / TTA×1 0.3997（每个房间都更低），AB-UPT 0.3718 / 0.3721；两者都达标。AB-UPT 整网格每房 215–303 s（每个查询对全部节点做注意力，比 AI 初始化后的 CFD 还慢），TTA 15–19 s，所以它的卡设为自动优先 TTA。
- 同时修了：预热只在整网格放得下时用房间输入；每次推理后归还显存缓存（实测不影响速度），推理进程闲时约 0.6 GB；复制或移动过的算例写 AI 结果时读到原算例的网格路径（graph.pkl 里的绝对路径），现在按工作目录自己的 t1 读取；推理进程启动门槛从 14 GiB 降到 6 GiB。
- 浏览器实测（8090，GPU 5）：Base2-9 副本自动 → TTA，126 次前向，88 s，峰值 11.6 GiB，后处理打开 650 万单元、T 15.1–47.2 °C（训练范围外的提示照常列出）；DCTS 强制 TTA 12 s（21 次前向，3.7 GiB），自动仍为整网格 2.1 s（10.2 GiB）；实时调参请求 TTA×2 生效。Base2-9 在这份网格上没有 CFD 真值，结果是泛化测试，不是测得的误差。

## 2026-10-29 大算例性能第一轮（Alibaba-hongchou，1038 万单元，进行中）

- 前端（开发版页面实测，headless Chromium + RTX 4090）：每帧主线程开销约 37 ms → 13–15 ms（27 fps → 60 fps 封顶），draw call 955 → 495。原因与修法：399 个机柜门（每个一份材质）和若干透明面板是"透明 + 双面"材质，three 对它们每帧分两遍画、每遍重新求着色器参数（帧时间的四分之一）——平面几何改为一遍绘制，像素不变（`geometry/singlePassSheets.ts`，曲面与有厚度的半透明体仍两遍）；静态合批每帧的检查改为按父节点缓存可见性、外观先比廉价指纹再比全量并分摊到 30 帧（否则每 30 帧多 50 ms），BatchedMesh 不再逐实例做视锥裁剪。

## 2026-10-30 dcCart 壳体裁切调度（Alibaba-hongchou）

- 原因：8 进程时每个 rank 自己裁切约 60 s，整段却要 277 s。一排 13 个机柜块沿 x 首尾相接，相邻两块由相邻两个 rank 共有；按壳体编号逐个裁切时，rank 2 等 0 和 1、rank 3 等 2……排成一条链。
- 修法（`dcCartCutCells.C` 的 `scheduleCarving`）：各 rank 报每个壳的 reach 单元数与 reach 包围盒，合并后所有 rank 用同一份数据排出同一个顺序。reach 盒有体积重叠的壳保持编号先后；只在同一网格面上相接的不共享单元，顺序放开。估算收益不到 10% 时保持编号顺序；单进程与 `DCCART_CARVE_IN_INDEX_ORDER` 也保持。
- 结果：裁切 277 → 80 s，网格阶段 594 → 399 s。网格与编号顺序的网格全局一致：Alibaba-hongchou（8 进程）34,155,564 面 / 7,990 patch，Base604（8 进程）22,854,403 / 4,336，Shinaide（4 进程）2,379,639 / 337，按面中心多重集与各 patch 面数逐一相同（编号不同，所以文件不逐字节相同）。完全放开顺序则网格改变（多 10,031 个阶梯单元），因此重叠的壳必须保序。说明见 `DCCARTMESH.md`「Carving order at several ranks」；`DCCART_SHELL_TRACE=<dir>` 写逐壳耗时与等待。

- 现象：盲板全封、通道封闭的工程，冷通道里仍有热风，进风最高约 30 °C；网格只有 8 个区域（应为房间 + 8 个热通道），I/J 热通道与房间相连。
- 原因一（几何）：I/J 顶板 IJ4 的边离 J10、J13 柜背差 6 mm。缝隙检测把 IJ4 越过门 IJ2 的 2 mm 搭接当成"有意开口"，跳过了整条边。已修检测（`meshPreflight.ts`），两个 CMI 工程 IJ4 补长 6 mm（`8335281f7`）。
- 原因二（网格，主因）：J7 等 11 个机柜位于 z=11.6079995，导出的 STL 里同一前面一部分写成 11.728，一部分写成 11.727999。dcCart 的坐标吸附把两者合成同一值，但没有合并点编号；机箱按点编号连通成壳，于是被拆成开口的碎片、按薄板切割，NF5280M5 的风扇面只剩 54–72%，约 11 m³/s 热风穿过这些机箱进入冷通道。两种吸附现在都与焊接一样合并重合点（`setMovedPoints`）；运行器在网格后检查每个服务器风扇面的面积（低于 STL 面积的 80% 即告警，验收门判失败）。
- 验证：fullBlock 重网格重算，9 个区域，冷区不含任何排风口，1673 个进风口 20.2–20.3 °C，I/J 通道进出 21.65 m³/s 平衡，169 步收敛，能量 1519.5 / 1519.7 kW。十个发布算例与 CMI-Guichou 典型缝隙工程重网格：严格 checkMesh 全部 accepted / 0，无 stair-step 切割，无风扇面缺失。

## 2026-11-11 GPU 风冷求解器并入（可选求解引擎，已完成）

- **代码在仓库里**：`src/backend/aircooling/gpu_solver/` 是本项目的 GPU 求解器（可微的 Newton–Krylov 有限体积求解器，稳态 Boussinesq k-ε，残差与 Jacobian 向量积由 Warp 核在显卡上完成），由 `tools/vendor_gpu_solver.py` 从求解器开发仓库逐字拷入，`VENDORED.json` 记来源提交与每个文件的 SHA-256。它与后端同在 `dcdtuni` conda 环境里运行（`gpu-solver` extra：warp-lang、pyamg、h5py）。
- **怎么用**：`start_server.sh --gpu`（全部显卡）或 `--gpu <列表>` 启动后，求解页出现「求解引擎」选择（默认仍是 OpenFOAM）；脚本化 API 用 `--solver-engine gpuNewton`，私有服务器自动带 `--gpu`。没带 `--gpu` 的服务器不提供这个引擎，请求会被拒绝。`--gpu` 同时是 Kit 与 AI 推理取显卡的列表（`--ov-gpu`、`--ai-gpu` 可各自改），AI 推理的开关仍是 `--scano`。
- **同一条链路**：运行目录、字典、边界条件、停止判据（回风温度平台与能量闭合）、监测文件与结果目录都和 OpenFOAM 一样，执行回执、传感器、收敛判定与场指标由同一套代码生成；一张网格可以先后交给两个引擎求解。
- **验证**：六个机房族（行间与周边送风，各有开放、冷通道封闭、热通道封闭）经脚本化 API 用仓库内的求解器逐一求解，全部判为 `CONVERGED`，ACU 回风温度、机柜进风最高温、流量与能量闭合都落在与 OpenFOAM 对照的登记判据之内。行间送风的三个族求解阶段用时不到 OpenFOAM 的一半；周边送风的族与 OpenFOAM 相当，其中一个族更慢。求解器进程按需常驻（第一次 GPU 求解时启动，空闲 10 分钟后退出），之后的求解不再等待加载。逐次运行的记录在求解器开发仓库的研究记录里（2026-11-11，V3）。
- **显卡监视与显存不足**：求解页选中 GPU 求解器时，实时显示本次启动可用的每张显卡（已用与空闲显存、利用率、求解器在该卡上是求解中还是待命）、当前网格的单元数与一次求解至多需要的显存（`GET /api/gpu-solver/status`，2 秒一读）。一次求解用一张卡，约需 0.8 GiB + 每百万求解单元 18 GiB（50 万单元以下按每百万 25 GiB；六个机房族与本仓库八个机房实测，24 GB 的卡约容纳 120 万单元）。求解器读完网格后先比对所在显卡的空闲显存，放不下就在时间推进之前终止；求解中途分配失败同样归为显存不足。两种情况页面都显示报错并提示：重新启动 `start_server.sh`，用 `--gpu` 指定更多或空闲显存更大的显卡。
- **下一步补**：周边送风机房的线性求解代价（每步 GMRES 次数）；求解前约半分钟的运行目录准备；降低每单元显存（让更大的机房放进一张 24 GB 的卡），以及多卡分区求解。
