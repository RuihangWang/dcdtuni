# cfdrun Rename + bridge_bc In-Memory Design Spec

**Date**: 2026-04-11
**Status**: Draft (awaiting user review)
**Scope**: Rename `case/<name>/model/cfd_export.json` to `<basename>.cfdrun`, and refactor `bridge_bc.json` from a disk file into an in-memory `BridgeBCRegistry` injected into `FieldGenerator`.

---

## 1. Background

### 1.1 Today's data flow

```text
STLGeneratorForOpenFoam/projects/<name>.cfdproj    (frontend editor state)
        │
        ▼  buildCfdExportJson()  (JS, ~150 lines, projection)
        │
[POST cfdExportJson + stlFiles[]]  → server.py
        │
        ▼  落盘
case/<name>/model/cfd_export.json  +  Mesh/constant/triSurface/*.stl
        │
        ▼  STLGenRunner reads cfd_export.json (CFDExport schema)
        ▼  _build_and_save_bridge_bc()  →  case/<name>/model/bridge_bc.json
        ▼  FieldGenerator.load(bridge_bc.json)
        ▼  blockMesh + snappyHexMesh + buoyantBoussinesqSimpleFoam
```

`case/<name>/model/` after a run contains:

```text
model/
├── cfd_export.json     ← frontend POST
├── bridge_bc.json      ← backend derived (intra-process artifact)
├── liquid_results.json ← liquid solve cache (only if liquid cooling enabled)
└── room.json           ← legacy DCTwin stub, auto-cleaned by runner each run
```

### 1.2 Pain points motivating this change

- **Visual clutter**: Three to four JSON files in `model/`, two of which are generated by different actors and have unrelated purposes.
- **Naming confusion**: `cfd_export.json` is a generic name; users cannot tell which `.cfdproj` it was generated from.
- **`bridge_bc.json` is a phantom artifact**: It is written by `STLGenRunner` and then re-read by three call sites within the same Python process — pure intra-process indirection that does not need to touch disk.

### 1.3 Pain points NOT addressed by this change (explicit non-goals)

This refactor is **purely cosmetic + an internal cleanup**. It does NOT solve:

- Schema drift between JS `buildCfdExportJson()` and Python `CFDExport` (still two implementations of the same projection logic in two languages).
- Single source of truth for the CFD field set (the JS projection logic remains the de facto authority).
- Backend independent run from `.cfdproj` alone (the backend still consumes the projected `.cfdrun`, not the raw cfdproj).

The user explicitly chose to descope all of the above after seeing the implementation cost (~1000 lines of JS naming logic that would have to be ported to Python). Those goals can be revisited later as a separate project.

## 4. Filename resolution rule

The frontend computes the cfdrun filename via a new helper `getCfdrunFilename()` with the following resolution order:

1. **If a `.cfdproj` is currently loaded or saved** (i.e. `getCurrentRemoteProjectFile()` returns a non-empty path): use the cfdproj basename without extension, append `.cfdrun`.
2. **Else fall back to the web UI's project name**: `sanitizeName(state.projectName || state.exportFileName || 'project') + '.cfdrun'`.

### Examples

| User state | Resulting cfdrun filename |
|---|---|
| Loaded `STLGeneratorForOpenFoam/projects/base604_1774199140766.cfdproj` | `base604_1774199140766.cfdrun` |
| Loaded `STLGeneratorForOpenFoam/projects/CMI-Guichou.cfdproj` | `CMI-Guichou.cfdrun` |
| No cfdproj loaded; UI has `state.projectName = "MyTest"` | `MyTest.cfdrun` |
| No cfdproj loaded; UI has `state.exportFileName = "Trial7"` (no projectName) | `Trial7.cfdrun` |
| No cfdproj loaded; nothing set in UI | `project.cfdrun` |

`sanitizeName()` is the existing JS helper that maps to OpenFOAM-safe identifier characters (`[A-Za-z0-9_]`).

## 5. Architecture: bridge_bc in-memory refactor

### 5.1 Why `bridge_bc.json` exists today

`BridgeBCRegistry` is the **domain-language → OpenFOAM-language translation table**. Two stages:

- **Stage 1 (heavy)**: `STLGenRunner._build_and_save_bridge_bc()` walks the parsed `cfd_export.json` and converts user concepts (rack/fanServer/ACU/leakage/wall_baffle/...) into a flat `{ patch_name → BCSpec }` map. This is where all the "what BC type does this STL solid get" logic lives, across 11 distinct `bc_type` values.
- **Stage 2 (light)**: `FieldGenerator._collect_imported_bc_data()` iterates the registry and renders Jinja2 templates for `0/U`, `0/T`, `0/p_rgh`, etc. This stage knows nothing about racks or ACUs — only about patches and BC types.

The registry abstraction is genuinely valuable: it decouples Stage 1 (which understands cfd_export schema) from Stage 2 (which understands OpenFOAM templates). **This decoupling is preserved.** Only the disk persistence is removed.

### 5.2 Why disk persistence is unnecessary

All three current consumers of `bridge_bc.json` are within the same Python process during the same run:

| Consumer | Current call | Location |
|---|---|---|
| Field BC generation | `BridgeBCRegistry.load(path)` | `fields.py:_collect_imported_bc_data()` line 128 |
| Leakage fvOptions config | `json.load(bridge_bc_path)` | `stlgen_runner.py:_build_leakage_fvoptions_config()` line 883 |
| Wall baffle boundary patch | `json.loads(bridge_path.read_text())` | `stlgen_runner.py:_ensure_wall_baffles_are_wall_type()` line 2981 |

There are **zero external consumers**: no scripts, no tests, no `server.py` endpoints, no debug tools depend on `bridge_bc.json` existing on disk. Documentation references in `.claude/CLAUDE.md`, `STLGeneratorForOpenFoam/Instruction.md`, and historical specs are descriptive only.

### 5.3 Replacement for debug visibility

The one genuine value of the on-disk file was being able to `cat` it during debugging to see what BC was assigned to which patch. This is preserved via a `logger.info` summary line emitted at the end of `_build_bridge_bc()`:

```python
from collections import Counter
counts = Counter(spec.bc_type for _, spec in self._bridge_registry.items())
summary = " | ".join(f"{n} {bc}" for bc, n in sorted(counts.items()))
logger.info(f"Built BridgeBCRegistry: {len(self._bridge_registry)} patches | {summary}")
```

Sample output: `Built BridgeBCRegistry: 47 patches | 8 acu_supply | 8 acu_return | 12 fan_inlet | 12 fan_outlet | 4 wall_baffle | 3 leakage_zone`.

If, in the future, full per-patch detail is needed for debugging, a hidden environment variable (e.g. `DCDTUNI_DUMP_BRIDGE_BC=/tmp/bridge.json`) can be added — but this is **out of scope for this refactor** and will only be implemented if the summary line proves insufficient in practice.

## 6. Code change inventory

### 6.1 Frontend — `STLGeneratorForOpenFoam/web/STL_generate.html`

- **Add** `getCfdrunFilename()` helper near other filename helpers (e.g. near line 12060).
- **Modify** `runMeshGeneration()` (around line 23015): the POST body to `/api/prepare-case` and `/api/run-mesh` gains a new field `cfdrunFilename: getCfdrunFilename()`. The existing `cfdExportJson` field stays as-is.
- **Do NOT touch** `buildCfdExportJson()`. Its body is unchanged.
- **Do NOT touch** the `saveProject()` flow or the `.cfdproj` save path.

### 6.2 Server — `STLGeneratorForOpenFoam/server/server.py`

- **Modify** `handle_prepare_case()` and `handle_run_mesh()`:
  - Read `cfdrunFilename: str | None = data.get("cfdrunFilename", None)` from the POST body.
  - If absent or empty, fall back to `"project.cfdrun"` (mirrors the JS fallback).
  - Compute `cfdrun_path = model_dir / cfdrunFilename` and write the JSON content there instead of `model_dir / "cfd_export.json"`.
  - Update the constructed shell command from `--from-stlgen <cfd_json_path>` to `--from-cfdrun <cfdrun_path>`.
- **Modify** `_clear_stlgen_tri_surface_upload_artifacts()` (or its caller): when writing a new `.cfdrun`, also delete any pre-existing `model/cfd_export.json` and `model/bridge_bc.json` if present (one-time migration cleanup at write time, before the runner is invoked).

### 6.3 Backend CLI — `src/backend/aircooling/runner/run_cfd.py`

- **Rename** the CLI flag `--from-stlgen` to `--from-cfdrun`.
- **Update** the help text and module docstring to refer to `.cfdrun` files.
- **No changes** to argument parsing logic — the file pointed to has identical content/format.

### 6.4 Backend runner — `src/backend/aircooling/runner/stlgen_runner.py`

- **`__init__`**: add `self._bridge_registry: Optional[BridgeBCRegistry] = None`.
- **Rename** `_build_and_save_bridge_bc()` → `_build_bridge_bc()`:
  - Remove the `registry.save(bridge_bc_path)` call.
  - Store the registry on `self._bridge_registry`.
  - Append the `logger.info` summary line described in §5.3.
- **Modify** `_build_field_generator()`: pass `bridge_registry=self._bridge_registry` to `FieldGenerator(...)`.
- **Modify** `_build_leakage_fvoptions_config()`:
  - Replace `json.load(open(bridge_bc_path))` with `self._bridge_registry.items()`.
  - Adapt the iteration: items yield `(name, BCSpec)` tuples; access `spec.bc_type`, `spec.sigma`, etc. via attributes instead of dict keys.
- **Modify** `_ensure_wall_baffles_are_wall_type()`:
  - Replace `json.loads(bridge_path.read_text())` with `self._bridge_registry.items()`.
  - Build the `wall_patches` set the same way: `{name for name, spec in self._bridge_registry.items() if spec.bc_type == "wall_baffle"}`.
- **Modify** `_cleanup_stale_compat_files()`:
  - Add: if `model/bridge_bc.json` exists, unlink it and log "Removed stale bridge_bc.json (now in-memory)".
  - Add: if `model/cfd_export.json` exists, unlink it and log "Removed stale cfd_export.json (replaced by .cfdrun)".

### 6.5 Backend FieldGenerator — `src/backend/aircooling/runner/fields.py`

- **`FieldGenerator.__init__`**: add new keyword parameter `bridge_registry: Optional["BridgeBCRegistry"] = None`. Store on `self.bridge_registry`.
- **Modify** `_collect_imported_bc_data()`: replace the disk-load block with an in-memory iteration. The `imported_bc` dict construction (mapping `BCSpec` attributes to dict keys) is **identical** to today's body — only the source of `registry` changes.

  Today's code (lines 128-141):

  ```python
  bridge_bc_path = self.case_dir / "model" / "bridge_bc.json"
  if bridge_bc_path.exists():
      from dcdtuni.runner.bridge_bc import BridgeBCRegistry
      registry = BridgeBCRegistry.load(bridge_bc_path)
      for patch_name, spec in registry.items():
          imported_bc[patch_name] = {
              "bc_type": spec.bc_type,
              "temperature": spec.temperature,
              "flow_rate": spec.flow_rate,
              "power": spec.power,
              "sigma": spec.sigma,
              "heat_flux": spec.heat_flux,
          }
      logger.debug(f"Loaded {len(registry)} bridge BC entries from {bridge_bc_path}")
  ```

  Becomes:

  ```python
  if self.bridge_registry is not None:
      for patch_name, spec in self.bridge_registry.items():
          imported_bc[patch_name] = {
              "bc_type": spec.bc_type,
              "temperature": spec.temperature,
              "flow_rate": spec.flow_rate,
              "power": spec.power,
              "sigma": spec.sigma,
              "heat_flux": spec.heat_flux,
          }
      logger.debug(f"Loaded {len(self.bridge_registry)} bridge BC entries from in-memory registry")
  ```

  The `from dcdtuni.runner.bridge_bc import BridgeBCRegistry` line moves to a top-level type hint import (only needed for the constructor type annotation).

### 6.6 Backend BridgeBCRegistry — `src/backend/aircooling/runner/bridge_bc.py`

- **Delete** `BridgeBCRegistry.save()` method.
- **Delete** `BridgeBCRegistry.load()` classmethod.
- **Update** module docstring to reflect "in-memory only" status; remove the file-based usage example.
- **Keep** `register()`, `get()`, `items()`, `__contains__`, `__len__`, `BCSpec`, `_sanitize()`.

## 7. Final state of `case/<name>/model/`

After this refactor, a fresh run of any case produces:

```text
case/<name>/
├── model/
│   ├── <basename>.cfdrun         ← frontend POST writes (was cfd_export.json)
│   └── liquid_results.json       ← liquid solve cache (only if liquid enabled)
├── Mesh/
│   ├── constant/triSurface/      ← frontend POST writes
│   ├── constant/polyMesh/        ← snappyHexMesh produces
│   ├── system/                   ← runner produces
│   └── 0/                        ← runner produces
└── log/
    └── <timestamp>_<solver>/     ← solver run output
```

For comparison, today's state:

```text
case/<name>/model/
├── cfd_export.json               ← will become <basename>.cfdrun
├── bridge_bc.json                ← will be deleted (in-memory)
├── liquid_results.json           ← unchanged
└── room.json                     ← already auto-cleaned by runner
```

Net change in `model/`: **two fewer files** (`bridge_bc.json` deleted, `cfd_export.json` renamed but still one file).

## 8. Migration

**No automated script.** Existing cases are migrated user-driven via the existing API:

1. User loads the corresponding `.cfdproj` from `STLGeneratorForOpenFoam/projects/` in the browser (or via `curl POST /api/load-cfdproj`).
2. User clicks "Run Mesh" (or `curl POST /api/run-mesh`).
3. `server.py` writes `<basename>.cfdrun` + STL files into `case/<name>/`, deleting any pre-existing `cfd_export.json` and `bridge_bc.json` at write time.
4. Runner starts; `_cleanup_stale_compat_files()` deletes any remaining stale files.
5. After this single run, the case directory is fully migrated.

**4 orphan cases** (`base`, `base301`, `CMI-Germany`, `leakage_test`) have no source `.cfdproj` and are not auto-migrated. The user will rebuild them manually in the frontend if/when they need to be re-run.

This migration approach is consistent with the project's CLAUDE.md rule: *"所有调试和测试必须通过 server.py 的 REST API 触发，禁止直接 CLI 运行 dcdtuni 命令"*.

## 10. Risks and rollback

### 10.1 Risks

| Risk | Likelihood | Mitigation |
|---|---|---|
| Unit tests / scripts in `tests/` import `BridgeBCRegistry.load()` | Low — grep showed no consumers | Re-grep before deletion; if found, update them |
| External tools or notebooks read `model/bridge_bc.json` | Very low — repo-wide grep showed zero non-runner consumers (see §5.2) | Confirm the assumption with the user before deleting `BridgeBCRegistry.load()`. If any external consumer surfaces later, restore `load()` as a thin wrapper that reads a hand-rolled debug dump produced via the future `DCDTUNI_DUMP_BRIDGE_BC` env var (§11). |
| Changing `_build_leakage_fvoptions_config()` to read from `BCSpec` attributes instead of dict keys causes a subtle field-name mismatch | Medium — manual translation required | Cover with the unit test in §9.2; cross-check field names against `BCSpec` Pydantic model |
| Frontend `getCfdrunFilename()` produces a name with characters that confuse the OS or OpenFOAM | Low — `sanitizeName()` is the same helper used elsewhere | Test in §9.3 with edge cases |
| Old cases that someone is mid-debugging on still have `cfd_export.json` and break under the new runner | Medium | Runner deletes both stale files in `_cleanup_stale_compat_files()` AND server.py deletes them at write time. Worst case: user re-runs once. |

### 10.2 Rollback

This refactor is a single PR / single commit boundary. Rollback = `git revert`. No data migration to undo (the `.cfdrun` file is exactly the same content as the old `cfd_export.json` — restoring the old runner just means the user must rename the file back, or re-run from the frontend to regenerate).

## 11. Out-of-scope follow-ups (parking lot)

These were discussed during brainstorming and explicitly descoped from this refactor. If they become important later, they get their own spec:

- **Schema-drift elimination** between JS `buildCfdExportJson()` and Python `CFDExport` (would require porting ~1000 lines of JS naming/topology logic to Python; large undertaking).
- **`liquid_solve_log/<timestamp>/` archive** for liquid solve results, mirroring the main `log/` structure.
- **Backend independent run from `.cfdproj`** (would require the schema-drift work above as a prerequisite).
- **Python STL generator** (massive — the JS STL exporter is ~7000 lines).
- **Cleanup of `STLGeneratorForOpenFoam/projects/`** vs case-dir as the cfdproj home.
- **Hidden `DCDTUNI_DUMP_BRIDGE_BC` env var** for full per-patch debug dump (only if `logger.info` summary proves insufficient).
