# Auto-CFD Workflow Skills Design

**Date:** 2026-05-12
**Status:** Approved
**Scope:** 5 Claude Code skills for automated data center CFD workflow + dataset generation

---

## 1. Motivation

This project supports a paper demonstrating "automated CFD" for data centers. The core innovation is **"script-defined engineering + exposing native API to agents"** — distinguishing from foamAgent (black-box) and openfoamGPT (pure LLM generation) by letting an LLM agent drive real CFD toolchains through structured APIs.

The deliverables are:
1. **5 Claude Code skills** that together form an end-to-end automated CFD pipeline
2. **A dataset of 13-15 cases** for evaluation, generated by reverse-engineering existing cfdproj files

---

## 2. Architecture Overview

### Skill Chain

```
User input (image + prompt)
       │
       ▼
  dc-interpret         →  dc-params.json (structured parameters)
       │
       ▼
  dc-build-cfdproj     →  .cfdproj file (via headless browser JS API)
       │
       ▼
  dc-run-cfd           →  Completed case (mesh + solve via server API)
       │
       ▼
  dc-analyze           →  Analysis report (convergence + ACU return temperature)


  dc-dataset-reverse   →  Batch-generate input/label pairs from existing cfdproj files
```

### 5 Skill Overview

| Skill | Input | Output | Core Technology |
| ----- | ----- | ------ | --------------- |
| `dc-interpret` | 2D image + text prompt | `dc-params.json` | Claude vision + parameter completeness checking |
| `dc-build-cfdproj` | `dc-params.json` | `.cfdproj` file | Frontend JS API via `/api/browser/exec-js` |
| `dc-run-cfd` | `.cfdproj` | Completed case (mesh+solve) | Server API full pipeline orchestration |
| `dc-analyze` | Case directory | Analysis report | Residual + ACU return temperature + heat balance |
| `dc-dataset-reverse` | Existing cfdproj files | `input/` + `label/` pairs | Reverse-generate training/evaluation dataset |

### Technology Stack

- **Vision understanding:** Claude's built-in multimodal capability
- **Scene construction:** `/api/browser/exec-js` → frontend JS API (Three.js)
- **CFD execution:** `/api/browser/full-pipeline`, `/api/run-mesh`, `/api/job-status`
- **Result analysis:** `/api/probes-latest`, OpenFOAM postProcess utilities

## 3. Intermediate Data Format: `dc-params.json`

Output of `dc-interpret`, input of `dc-build-cfdproj`. High-level semantic description (not low-level cfdproj).

```jsonc
{
  "projectName": "paintToDC1",
  "room": {
    "width": 14,           // X direction (m)
    "depth": 7,            // Z direction (m)
    "height": 3,           // Y direction (m)
    "polygon": [[0,0],[14,0],[14,7],[0,7]]  // optional, for non-rectangular rooms
  },
  "rackColumns": [
    {
      "name": "Col1",
      "count": 6,                       // racks in this column
      "startPosition": [2.5, 0, 1.3],   // anchor of first rack
      "spacing": 0.8,                   // rack-to-rack spacing along Z
      "orientation": 90,                // Y-axis rotation (degrees)
      "rackSize": {"W": 0.8, "D": 1.2, "H": 2.2},
      "equipments": [
        {
          "kind": "fanServer",
          "name": "fan-server_1",
          "startUnit": 29,
          "spanUnits": 5,
          "power_W": 5000,
          "flowRate_m3s": null           // null = auto
        }
      ]
    }
  ],
  "acus": [
    {
      "name": "ACU_Left_1",
      "position": [1.3, 0, 1.5],
      "size": {"W": 1.8, "D": 1.0, "H": 2.0},
      "orientation": -90,
      "supply": {
        "face": "front",
        "temperature_C": 18,
        "flowRate_m3s": 2.5,
        "velocity_ms": null,
        "direction": [0, 0, -1]
      },
      "return": {
        "face": "top",
        "direction": [0, 0, -1]
      }
    }
  ],
  "baffles": [
    {
      "name": "Baffle_HA1_South",
      "position": [5.0, 0, 2.5],
      "size": {"W": 4.0, "D": 0.01, "H": 2.2},
      "orientation": 0
    }
  ],
  "cfdSettings": {
    "solverType": "steady",
    "meshBaseSize": 0.34,
    "maxGlobalCells": 1000000,
    "parallelCores": 8,
    "endTime": 1000,
    "roomTemperature_C": 22
  }
}
```

Key design decisions:
- Rack columns described by `count` + `spacing`, not per-rack coordinates — reduces LLM output and error surface
- Physical units are explicit in field names (`_W`, `_C`, `_m3s`, `_ms`)
- `null` values mean "use tool default"

## 4. Skill: `dc-interpret`

### Purpose

Analyze user's 2D floor plan image + text prompt → extract data center layout parameters → check completeness → ask user for missing info or mock defaults → output `dc-params.json`.

### Parameter Completeness Checklist

| Parameter | Extractable from image? | Must user provide? | Mock default |
|-----------|------------------------|-------------------|--------------|
| Room dimensions (L×W×H) | Approximate ratio | Precise values needed | 10×6×3 m |
| Rack column count & racks per column | Yes (countable) | No | — |
| Rack orientation (inlet→outlet) | Yes (arrows) | No | — |
| Rack dimensions (W×D×H) | No | Preferred | 0.6×1.2×2.2 m |
| Per-rack power | No | Preferred | 5 kW |
| Server U-slot distribution | No | Optional | Single 5U fan-server |
| ACU count & positions | Yes (countable) | No | — |
| ACU supply temperature | No | Preferred | 18°C |
| ACU supply flow rate | No | Preferred | 2.5 m³/s |
| ACU return position | Yes (annotated) | No | Top face |
| Hot/cold aisle containment | Yes (annotated) | No | — |
| Containment top lid | Partially visible | Preferred | No lid |
| Solver parameters | No | Optional | steady, 8 cores, meshBase=0.34 |

### Interaction Flow

1. Use Claude vision to analyze the image, extract visible layout information
2. Parse text prompt, merge parameters
3. Compare against checklist, categorize into:
   - Acquired parameters (show with checkmark)
   - Missing but important (ask user)
   - Missing but mockable (show default, let user override)
4. Present a single consolidated summary to the user
5. After user responds, generate `dc-params.json` and save to case directory

### Rules

- Never guess precise numerical values from image — image provides topology only (how many columns, which side ACUs are on), precise dimensions must come from prompt or user confirmation
- Mock defaults are based on ASHRAE standard data center values
- If user says "use all defaults", skip all missing items at once

## 5. Skill: `dc-build-cfdproj`

### Purpose

Read `dc-params.json` → start server if needed → programmatically build the complete scene via `/api/browser/exec-js` → save as `.cfdproj`.

### Prerequisites

- Server running (skill checks, auto-starts if needed)
- Headless browser ready (auto-initialized on first `/api/browser/*` call)

### Construction Steps

```
Step 0: Environment setup
  - Verify server running (GET /api/server-info)
  - If not: start server with conda run -n dcdtuni
  - Login (POST /api/auth/login)

Step 1: Initialize empty scene
  - exec-js: clear state.models
  - exec-js: setProjectName(), setExportFileName()

Step 2: Configure room
  - exec-js: state.roomPolygon = {vertices, height}
  - exec-js: setProjectBounds() for each axis
  - exec-js: updateCfdRoom('height', H)

Step 3: Create Floor + Ceiling
  - createDefaultFloorModel() × 2
  - Set anchors and dimensions to match room

Step 4: Create Walls (4 walls for rectangular room)
  - createDefaultWallModel() × 4
  - Set anchor, base(W,D,H), rotation for each edge

Step 5: Create Rack Columns (core loop)
  FOR each rackColumn:
    FOR i in range(count):
      - createDefaultRackModel()
      - Get new model id: state.models[state.models.length-1].id
      - updateModel(id, anchor.x/z, position)
      - updateModelRotation(id, 'y', orientation)
      - updateRackModel(id, W/D/H, size)
      - updateModelName(id, name)
      FOR each equipment:
        - createRackEquipmentAtSlot(id, 'front', startUnit, kind)
        - Get equipment id from rack.equipments array
        - updateRackServerCfd(id, eqId, 'power', power_W)

Step 6: Create ACUs
  FOR each acu:
    - createDefaultAcuModel()
    - Set anchor, size, rotation, name
    - addPatch(id, supply.face, 'rect')
    - updateAcuPatchPhysics(id, patchId, role/temperature/volumeFlowRate)
    - addPatch(id, return.face, 'rect')
    - updateAcuPatchPhysics(id, patchId, role='return')

Step 7: Create Baffles
  FOR each baffle:
    - createDefaultBaffleModel()
    - Set anchor, size, rotation, name

Step 8: Configure CFD parameters
  - setMeshConfig(meshBaseSize, maxGlobalCells)
  - setSolverConfig(endTime)
  - setSolverType('steady')
  - updateCfdRoom(solveProcess, roomTemperature)

Step 9: Save project
  - exec-js: saveProject() → get JSON
  - Write to {case_dir}/{projectName}.cfdproj
```

### Technical Details

- **Getting new model IDs:** After each `createDefault*Model()`, read `state.models[state.models.length-1].id`
- **Getting new patch IDs:** After `addPatch()`, read the last element of the corresponding face's `patches` array
- **Coordinate system:** X = room width, Y = height (y=0 is floor), Z = room depth
- **Rotation convention:** `updateModelRotation(id, 'y', degrees)` — 0° = front face toward -Z, 90° = front toward +X

### Verification

After construction:
1. `GET /api/browser/state` — confirm model count matches expected
2. `GET /api/browser/screenshot` — visual confirmation for user
3. If issues found, prompt user for adjustments

## 6. Skill: `dc-run-cfd`

### Purpose

Take `.cfdproj` → drive STL export + mesh generation + CFD solve through server API.

### Execution Flow

```
Step 0: Environment check
  - Verify server (GET /api/server-info)
  - Verify auth (GET /api/auth/check)
  - Set case dir (POST /api/set-case-dir)

Step 1: Export + mesh generation
  POST /api/browser/full-pipeline {
    "projPath": "...", "meshOnly": true
  }
  → Returns jobId

Step 2: Poll for mesh completion (every 10s)
  GET /api/job-status?jobId=xxx
  - Print recent log lines for user visibility
  - done=true, returncode=0 → continue
  - done=true, returncode≠0 → error, print last 20 lines, stop

Step 3: Mesh quality check
  POST /api/run-check-mesh
  - Parse checkMesh output
  - Multiple regions are NOT errors (CLAUDE.md rule 10)
  - Print key metrics (cell count, non-orthogonality, skewness)

Step 4: Start solver
  POST /api/browser/full-pipeline {
    "projPath": "...", "solveOnly": true
  }
  → Returns jobId

Step 5: Poll for solve completion (every 15s)
  GET /api/job-status?jobId=yyy
  - Print residual trends
  - done=true, returncode=0 → success
  - done=true, returncode≠0 → error, stop
```

### Error Handling

| Error | Action |
|-------|--------|
| Server not running | Auto-start, wait 30s |
| STL export failed | Print browser logs, suggest checking cfdproj |
| Mesh generation failed | Print last 20 log lines, common cause hints |
| checkMesh severe issues | Warn user, don't auto-abort |
| Solver divergence (NaN) | Print residual history, suggest lower relaxation |
| Poll timeout (30min) | Remind user, don't auto-abort |

### Mandatory Rules (from CLAUDE.md)

- Always parallel solve — never serial (rule 8)
- Always via server API — never `conda run` for business ops (rule 9)
- Process kill only via `fuser -k` — never kill/pkill (rule 3)

## 7. Skill: `dc-analyze`

### Purpose

After solve completion → check convergence → analyze ACU return temperatures → output analysis report.

### Analysis Flow

```
Step 1: Confirm solve completion
  GET /api/scan-case-status → check solveComplete flag

Step 2: Residual convergence check
  Extract residual history from solve log:
  - p_rgh target < 1e-4
  - U target < 1e-5
  - T target < 1e-5
  - k/epsilon target < 1e-4

Step 3: ACU return temperature analysis
  GET /api/probes-latest (or postProcess fallback)
  For each ACU return face:
  - Extract area-averaged T_return
  - Compute heat balance:
    Q_supply = ṁ × Cp × T_supply
    Q_return = ṁ × Cp × T_return
    Q_rack_total = Σ(all rack power)
    Balance error = |Q_return - Q_supply - Q_rack_total| / Q_rack_total
  - Steady-state criterion: balance error < 5%

Step 4: Generate report
  Output to conversation + save as {case_dir}/analysis_report.md
  Format:
  - Convergence table (residual / final value / target / status)
  - ACU return temperature table (ACU / T_supply / T_return / ΔT)
  - Heat balance summary (total rack power / total ACU heat removal / error %)
```

### Scope (intentionally limited)

- No flow visualization / slice plots / temperature contours
- No local hotspot analysis
- Only: residual convergence + ACU return temperature + heat balance

### Data Retrieval

Primary: `/api/probes-latest`
Fallback: `postProcess -func 'patchAverage(name=ACU_*_Return, T)'` via OpenFOAM CLI

## 8. Skill: `dc-dataset-reverse`

### Purpose

Reverse-engineer existing cfdproj files → generate dataset (2D screenshot + parameter description) → output to `demo_case/`.

### Per-Case Flow

```
Step 1: Load project
  POST /api/browser/load-proj {"path": "..."}

Step 2: Capture 2D top-down screenshot
  exec-js: applyViewPreset('top')
  GET /api/browser/screenshot?name=XXX_topview

Step 3: Extract parameters from cfdproj JSON
  Parse JSON with Python:
  - Room: roomPolygon + cfdRoom.height
  - Racks: count per column, orientation, dimensions, equipment, power
  - ACUs: count, position side, supply temp, flow rate
  - Baffles: hot/cold aisle containment
  - CFD: solver type, mesh size, cores

Step 4: Generate natural-language prompt.md
  Simulate realistic user description style, e.g.:
  "一个 14m×7m×3m 的数据中心机房。4 列服务器机柜，每列 6 个，
   左侧 2 列朝右送风，右侧 2 列朝左送风，形成 2 条热通道。
   每个机柜 43U，安装 1 台 5U 风扇服务器，功耗 5kW。
   左墙 2 台 ACU，右墙 2 台 ACU，送风 18°C, 2.5 m³/s, 顶部回风。
   热通道有南北挡板，无顶盖。"

Step 5: Organize output
  demo_case/{case_name}/
  ├── input/
  │   ├── topview.png
  │   └── prompt.md
  └── label/
      └── {case_name}.cfdproj
```

### Case Selection (from 19 available)

**Include (13):** Base604, Base2-9, Base_coldAisleIso, Base_leakage, CMI_China, CMI-Guichou, Alibaba_hangchou, Alibaba-sige, GTC_2025, STDCT, DMAL_Testbed, Shinaide, Slab

**Exclude:** paintToDC1 (already manual), Liquid (liquid-only), Shinaide_liquid (liquid), SingleRack (too simple)

**Pending:** Polygon_room, Tri_angle (non-rectangular — include if demonstrating generalization)

### Prompt Generation Strategy

- Not mechanical parameter transcription — simulate natural user description styles
- Randomly omit some parameters (power, mesh settings) so `dc-interpret` must handle incomplete input
- Vary verbosity across cases to test robustness

## 10. Paper Innovation Mapping

| Paper Narrative | Technical Implementation |
|----------------|------------------------|
| "Script-defined engineering" | cfdproj JSON schema + dc-params.json intermediate representation |
| "Exposing native API to agents" | `/api/browser/exec-js` → frontend JS API; `/api/browser/full-pipeline` → mesh+solve |
| "Unlike foamAgent's black-box" | Agent understands each API call's semantics, doesn't generate raw OpenFOAM dictionaries |
| "Unlike openfoamGPT's pure LLM generation" | Agent drives real toolchain through structured API, not generating mesh/BC text directly |
| "End-to-end verification" | dc-analyze automatically checks physical plausibility |
| "Generalizable dataset" | 13-15 diverse cases covering real-world data centers |
